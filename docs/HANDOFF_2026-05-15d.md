### Story 152 — Mekka Kernel Filter Chain (SK-inspired)
**Arquivo criado:**
- `src/services/invocation_filter.py` — SK-style filter chain completo:
  - `InvocationContext` dataclass: `function_name`, `arguments`, `result`, `exception`, `is_cancelled`, `metadata`, `started_at/ended_at`, propriedades `elapsed_s` e `succeeded`
  - `InvocationFilter` ABC: `async def invoke(ctx, next)` — cada filtro chama `await next()` para continuar (não chamar = cancelar)
  - `FilterChain`: pipeline recursivo com captura de resultado e exceção no contexto
  - Filtros built-in:
    - `AuditLogFilter` — loga função + elapsed (loguru, fail-silent)
    - `BenchmarkFilter` — registra latência no `pipeline_benchmark`
    - `CircuitBreakerFilter` — cancela quando `DEGRADED_MODE` ativo, seta `metadata["cancelled_reason"]`
    - `RetryFilter(max_retries, delay_s)` — retry com backoff configurável
    - `EventPublishFilter` — publica `{fn}.started` / `{fn}.completed` / `{fn}.failed` no EventBus
  - `MekkaFilterRegistry` singleton: `register()`, `build_chain(extra_filters=[])` — combina globais + extras
- `tests/test_story_152_invocation_filter.py` — 28 testes cobrindo contexto, chain básica, cancellamento, ordem de filtros, override de resultado, RetryFilter, CircuitBreakerFilter, Registry singleton

**Padrão SK:** Cada filtro recebe `(ctx, next)` onde `next` é coroutine sem args. Filtro decide se chama `await next()` (continua) ou não (cancela). Pós-processamento acontece após o `await next()`. Idêntico ao `FunctionInvocationFilter` do Semantic Kernel.

### Gates 5b + 5c no Batman (Stories 148+149)

Os gates são inseridos **após** o hard cap global de leverage (gate 5a — linha ~1175) e **antes** do "Final verdict" (gate 6). Isso garante que os gates de regime e tier sejam os últimos a ajustar leverage/size, e que o `breached` list capture todos os ajustes para o verdict REDUCED correto.

A ordem de precedência de leverage (da mais restritiva para a mais permissiva):
1. Gate 5a: hard cap global `_max_lev` (modo runtime)
2. Gate 5a: regime volatility cap (HIGH/EXTREME volatility via Thor)
3. Gate 5b: BEAR regime cap (`bear_regime_max_leverage`)

### PipelineBenchmark — design decisions (Story 151)

- `time.monotonic()` em vez de `datetime.now()` — monotônico, sem saltos de relógio, mais preciso para latência
- Rolling window de 500 ciclos = ~8h de ciclos a cada minuto
- `pipeline.slow_cycle` vai para o EventBus para que subscribers futuros (Telegram, dashboard WebSocket) possam reagir
- `__import__("time").monotonic()` no NickFury evita import no topo do módulo — fail-silent por design
- Percentis simples via sorted list (não numpy): sem dependência nova, suficiente para N=500

### Stories 152+153 — origem dos padrões SK

Os padrões implementados vêm da documentação do **Microsoft Semantic Kernel**:
- `@mekka_function` ← `@kernel_function` (SK Python SDK)
- `InvocationFilter` + `FilterChain` ← `FunctionInvocationFilter` (SK Python SDK)
- `MekkaPlugin` ← `KernelPlugin.from_object()` (SK Python SDK)
- `MekkaKernel` ← `Kernel` (central registry)
- `invoke_from_tool_call(name, arguments_json)` ← padrão OpenAI function calling dispatch

O separator `__` (duplo underscore) entre plugin e função é compatível com regex `^[a-zA-Z0-9_]+$` do OpenAI e permite split simples: `"trading__analyze".split("__", 1)` → `["trading", "analyze"]`.

### LLMCostTracker — registro idempotente (Story 147)

`get_llm_cost_tracker(auto_register=True)` chama `tracker.register()` que verifica `_subscribed` antes de adicionar ao EventBus. Múltiplas chamadas são seguras. O tracker usa `publish_sync()` do EventBus porque o `chat()` do LLMClient chama no `finally` síncrono.
